# 100,000 devices back online in 30 seconds

**Headline:** a fleet of 100,000 devices all reconnecting within 30 seconds, as after a network outage, checked in
completely on one Tracegale server running on a 6-core desktop processor. Not one device was turned away, and 99% got
their answer within 230 milliseconds. The whole server used less than 500 MB of memory.

## What was tested

Each device has its own private key and certificate, made by the server when the device was added, as for a real device.
To check in, a device opens its own encrypted connection (TLS with mutual certificates), sends `HELLO`, then a report of
its metrics, then closes the connection, as Tracegale's firmware does. Every check-in is written to the database before the
device gets its answer, so an answered check-in is never lost.

The test has every device check in once, with start times spread evenly over a window. A 30-second window is the worst case
the firmware allows: after an outage, each device waits a random time of up to 30 seconds before reporting
(`CONFIG_TRACEGALE_NET_WAKE_JITTER_S`). Day to day, the same fleet checking in hourly sends about 28 check-ins a second.

## The setup

- **Machine:** AMD Ryzen 5 8500G (6 cores, 12 threads), 16 GB of memory, Ubuntu 24.04 in a container. The server and the
  tool acting as devices shared this one machine.
- **Server:** Tracegale as it ships: the standard Docker Compose stack with nginx, the Tracegale server and PostgreSQL 16,
  nothing tuned. Commit `e769105`.
- **Devices:** `server/cmd/tgload`, a tool in the repository that acts as devices. The devices were created through the
  admin API, the same way a person adds them.

## Results

| Window | Checked in | Turned away (told to retry) | Time to answer `HELLO`: median / 95% / 99% / slowest | Check-ins a second |
|---|---|---|---|---|
| 120 seconds | **100,000 of 100,000** | 0 | 37 / 84 / 160 / 298 ms | 833 |
| **30 seconds** | **100,000 of 100,000** | **0** | **61 / 147 / 230 / 455 ms** | **3,322** |
| 15 seconds (beyond this machine) | 89,788 of 100,000 | 6,235 | 1.6 s / 15.2 s / 18.9 s / 32.8 s | 2,470 |

Each check-in is two messages, so the 30-second run is 6,644 messages a second, every one stored before its answer.

**Resources at their peak** (100% is one of the machine's 12 threads):

| | 120 seconds | 30 seconds |
|---|---|---|
| nginx, which does the encryption | 93%, 100 MB | 379%, 161 MB |
| Tracegale server | 37%, 75 MB | 102%, 113 MB |
| PostgreSQL | 33%, 180 MB | 96%, 185 MB |
| **Whole server stack** | **about 170% CPU, 380 MB** | **about 580% CPU, 480 MB** |

In the 30-second run the server stack used about half of the machine; most of the rest went to the tool acting as devices,
which does the other half of every encrypted connection.

## What it doesn't show

- **The 15-second run is past this machine's limit**, and shows what overload looks like rather than what the server can do:
  the tool itself ran short of CPU and delayed 70% of its starts. Devices were turned away or failed to connect, and this
  run didn't have them try again, as real firmware would. The next report,
  [1,000,000 devices](2026-11-15-load-1m.md), measures recovery with retries.
- **Only HTTPS.** Devices using MQTT weren't part of this test.
- **Only check-ins and metric reports.** Crash uploads, log records and firmware updates weren't part of the load.
- **One run of each window**, of one check-in per device, not a long run over days.
- **A single machine.** A server on a machine of its own, without the tool beside it, would do at least as well; that
  wasn't measured.

## How to repeat it

From a checkout of commit `e769105` or later, with Docker and Go 1.27:

```sh
cd server
python3 test/load_stack.py up /tmp/load          # a fresh test stack, its API token and CA, on ports 26443 and 26444
go build -o /tmp/tgload ./cmd/tgload
/tmp/tgload provision -admin https://127.0.0.1:26444 -token "$(cat /tmp/load/token)" -ca /tmp/load/server-ca.pem \
  -state /tmp/load/devices.jsonl -n 100000
/tmp/tgload checkin -device "$(cat /tmp/load/target)" -ca /tmp/load/server-ca.pem -state /tmp/load/devices.jsonl \
  -spread 30s -json /tmp/load/30s.json
python3 test/load_stack.py down
```

Raw results, including CPU and memory every 10 seconds and the server's own measurements every minute:
[data/2026-11-15-load-100k/](data/2026-11-15-load-100k/).

## Found and fixed by this test

The first run, on 2026-11-15 before the fix, turned 2.4% of devices away with a 99th percentile of 1.15 seconds: every
check-in waited for its database commit, and one writer committed every batch in turn. Four writers now commit in parallel,
each always handling the same devices, so a device's check-ins stay in order. Details: [docs/server/scale.md](../server/scale.md).
