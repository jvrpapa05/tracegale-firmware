# 600 million hostile inputs, no crash

**Headline:** every part of Tracegale that reads data from the other side of a connection was fed about **600 million**
machine-generated malformed inputs, built to find the cases a person wouldn't think of. Nothing crashed, read outside its
data, or behaved in an undefined way. The same fuzzing runs on every change, so a regression is caught before it ships.

## What was tested

Fuzzing feeds a program huge numbers of inputs, each mutated from the last ones that reached new code, to find inputs that
crash it or break its memory safety. Tracegale has two sides that read what the other sends, and either could be in hostile
hands:

- **The server** reads what devices send: their messages, metric reports, log records, crash dumps, and the firmware
  images administrators upload. A device in the field can be taken apart and made to send anything.
- **The firmware** reads what the server or MQTT broker sends: every reply, the MQTT protocol itself, and its own
  certificate. Encryption protects this traffic in transit, but if a server were ever compromised, these parsers are what
  stand between it and every device in a fleet.

| Side | Target | What it reads |
|---|---|---|
| Firmware | `wire` | Every message from the server |
| Firmware | `mqtt` | Everything an MQTT broker sends: connection and subscription replies, then messages, in pieces of any size |
| Firmware | `identity` | The device certificate, for the device's identity |
| Server | `wire` | Every message from a device |
| Server | `metrics` | Metric reports |
| Server | `logs` | Log records |
| Server | `crash` | Crash dumps |
| Server | `image` | Uploaded firmware images |

## The setup

- **Firmware:** the real C sources, built on the test machine with clang 18's libFuzzer, AddressSanitizer and
  UndefinedBehaviorSanitizer, which stop at the first out-of-bounds access, use of freed memory, or undefined behaviour.
  Small stand-ins replace the few Zephyr calls the MQTT client makes; the parsing code is unchanged. The harnesses also check
  that nothing handed back points outside the received data, and that nothing overflows its buffer. Harnesses:
  `firmware/tests/fuzz/`.
- **Server:** Go's built-in fuzzing, Go 1.27.4. Go is memory-safe, so these runs look for crashes, hangs and wrong answers.
- Each target ran for 10 minutes on one CPU thread, all at once, on the machine in [README.md](README.md), starting from
  what earlier runs had found. Commit `f032d54`.

crash.

## What it doesn't show

- **Fuzzing can't prove there are no flaws.** It finds what its inputs reach; a flaw behind a check it never got past can
  remain. The "new paths found" column shows the runs were still finding new code to explore, so longer runs can still add
  value.
- **The firmware ran on a PC, not a device.** The parsing code is the same, but differences in the compiler, the processor
  and the libraries mean a device isn't tested exactly as it runs.
- **Only the parsers.** Everything around them, such as the network code, TLS and storage, is checked in other ways.
- **10 minutes a target.** Fuzzing campaigns often run for days; that's planned as the code nears v1.

## How to repeat it

```sh
scripts/ci/fuzz-firmware.sh 600          # the firmware: needs clang with libFuzzer
cd server && go test -run=NONE -fuzz='^FuzzDecode$' -fuzztime=10m ./internal/wire     # and so on for each server target
```

The project's full checks and CI run both for a short time on every change. Raw results: [data/2026-11-15-fuzzing/](data/2026-11-15-fuzzing/).
