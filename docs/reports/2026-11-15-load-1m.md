# 1,000,000 devices on one server

**Headline:** one Tracegale server, on a single 6-core desktop processor with 16 GB of memory, handled a fleet of
1,000,000 devices, each with its own certificate.

- **A full fleet back after an outage:** all 1,000,000 devices reconnecting at once checked in completely within
  **8 minutes 51 seconds**, half of them within 3 minutes 50 seconds. Not one was lost; devices the server asked to wait
  simply tried again, as the firmware does.
- **A normal hour:** all 1,000,000 devices checking in once in an hour, the firmware's default, were all answered, none
  turned away, 99% within **57 milliseconds**.
- **Lightweight:** during that hour the whole server, encryption included, used on average **less than one CPU thread**
  (68% of one of the machine's 12) and **about 450 MB of memory**.

## What was tested

Each device has its own private key and certificate, made by the server through its admin API, as when a person adds a
device. To check in, a device opens its own encrypted connection (TLS with mutual certificates), sends `HELLO`, then a
report of its metrics, then closes the connection, as Tracegale's firmware does. Every check-in is written to the database
before the device gets its answer, so an answered check-in is never lost.

Three things were measured:

1. **Adding the fleet:** creating 1,000,000 devices through the admin API.
2. **Outage recovery:** every device reconnecting within 30 seconds, the most the firmware allows (it waits a random time of
   up to 30 seconds after its network returns). That's about 33,000 check-ins a second, far more than one machine can
   answer, so the server tells the devices it can't serve yet to try again later (`server_busy`), and each tries again 30 to
   60 seconds later, as the firmware does. The measure is how long until every device has checked in.
3. **A normal hour:** every device checking in once over an hour, the firmware's default interval, about 278 check-ins a
   second, with CPU, memory and storage sampled throughout.

## The setup

- **Machine:** AMD Ryzen 5 8500G (6 cores, 12 threads), 16 GB of memory, Ubuntu 24.04 in a container. The server and the
  tool acting as devices shared this one machine.
- **Server:** Tracegale as it ships: the standard Docker Compose stack with nginx, the Tracegale server and PostgreSQL 16,
  nothing tuned. Commit `e769105`.
- **Devices:** `server/cmd/tgload`, a tool in the repository that acts as devices, with up to 20,000 connections open at once.

## Results

### Adding the fleet

1,000,000 devices created through the admin API in **13 minutes 47 seconds**, 1,210 a second, none failed. Each one
got its own key and certificate from the server's certificate authority, and an entry in the audit log.

The registry of 1,000,000 devices takes **205 MB** in the database, about 205 bytes a device.

### Outage recovery: all 1,000,000 at once

| | |
|---|---|
| Devices that checked in | **1,000,000 of 1,000,000** |
| Every device checked in within | **8 min 51 s** (531 s) |
| Half of them within | 3 min 50 s; 95% within 7 min 42 s; 99% within 8 min 25 s |
| Times a device was asked to wait and tried again | 175,001 |
| Check-ins answered, on average | 1,885 a second over the whole recovery |
| Errors on the server | None. Every service stayed healthy, and answered normally straight after |

**Resources** (100% is one of the machine's 12 threads):

| | Average | Peak |
|---|---|---|
| nginx, which does the encryption | 254% CPU | 496% CPU, 1.2 GB |
| Tracegale server | 74% CPU | 135% CPU, 555 MB |
| PostgreSQL | 70% CPU | 108% CPU, 198 MB |

The tool acting as devices used 4.9 threads and 4.6 GB itself, on the same machine.

### A normal hour: 1,000,000 devices checking in hourly

| | |
|---|---|
| Devices that checked in | **1,000,000 of 1,000,000**, none turned away, no retries |
| Rate | 278 check-ins a second, steady, for one hour |
| Time to answer `HELLO`: median / 95% / 99% / slowest | **30 / 53 / 57 / 283 ms** |

**Resources over the hour** (sampled every 10 seconds; 100% is one of the machine's 12 threads):

| | Average CPU | Peak CPU | Average memory | Peak memory |
|---|---|---|---|---|
| nginx, which does the encryption | 32% | 40% | 38 MB | 39 MB |
| Tracegale server | 15% | 32% | 215 MB | 332 MB |
| PostgreSQL | 20% | 30% | 190 MB | 201 MB |
| Decoder and MQTT broker, idle | under 1% | 7% | 10 MB | 31 MB |
| **Whole server stack** | **68%, under 6% of the machine** | | **about 450 MB** | |

### Storage

Measured from the database before and after the hour, 1,000,000 check-ins later:

| | Each check-in | For 1,000,000 devices checking in hourly, a day |
|---|---|---|
| Check-in history | 180 bytes | 4.3 GB |
| Its metrics report | 291 bytes | 7.0 GB |
| **Together** | **473 bytes**, about 11 KB a device a day | **11.4 GB** |

How much a fleet keeps depends on how long records are kept, which an operator sets (`docs/server/README.md`,
"Settings"). For 1,000,000 devices checking in hourly, once the oldest records start to go:

| Kept | Disk |
|---|---|
| The defaults: check-ins 90 days, metric reports 30 days | about 600 GB |
| Both 30 days | about 340 GB |
| Both 7 days | about 80 GB |

The fleet's hourly totals of each metric are kept separately for 400 days, and take little space. A fleet of 10,000 devices
needs a hundredth of these figures. Old days are dropped whole, without slowing check-ins down.

## What it doesn't show

- **Recovery under 30 seconds.** No single machine answers a million devices in 30 seconds; the server spread the work over
  9 minutes by asking devices to wait, which the firmware is built to do. Answering faster needs more machines, which
  Tracegale doesn't support yet ([docs/server/scale.md](../server/scale.md)).
- **Only HTTPS.** Devices using MQTT weren't part of this test.
- **Only check-ins and metric reports.** Crash uploads, log records and firmware updates weren't part of the load.
- **Storage over months.** The storage figures are measured over one hour and multiplied out; a fleet running for months,
  with old days being dropped, wasn't run.
- **A single machine shared with the test tool,** which used about 5 of its 12 threads and 4.6 GB during the outage test.
  A server on a machine of its own would do at least as well; that wasn't measured.

## How to repeat it

From a checkout of commit `e769105` or later, with Docker and Go 1.27. Provisioning takes about 14 minutes, the outage test
about 9, and the hour an hour.

```sh
cd server
python3 test/load_stack.py up /tmp/load
go build -o /tmp/tgload ./cmd/tgload
/tmp/tgload provision -admin https://127.0.0.1:26444 -token "$(cat /tmp/load/token)" -ca /tmp/load/server-ca.pem \
  -state /tmp/load/devices.jsonl -n 1000000
# Outage recovery: everyone within 30 seconds, retrying as firmware does.
/tmp/tgload checkin -device "$(cat /tmp/load/target)" -ca /tmp/load/server-ca.pem -state /tmp/load/devices.jsonl \
  -spread 30s -retries 20 -json /tmp/load/outage.json
# A normal hour.
/tmp/tgload checkin -device "$(cat /tmp/load/target)" -ca /tmp/load/server-ca.pem -state /tmp/load/devices.jsonl \
  -spread 3600s -retries 20 -json /tmp/load/hour.json
python3 test/load_stack.py down
```

Raw results, including CPU and memory every 10 seconds and the server's own measurements every minute:
[data/2026-11-15-load-1m/](data/2026-11-15-load-1m/).

## Found and fixed by this test

Planning it showed that keeping check-ins would have cost too much at this scale: old check-ins were deleted one row at a
time, about 24 million deletions an hour at a million devices. Check-ins are now kept in one table partition a day, as
metrics and logs already were, so a whole day is dropped at once, and an index the old way needed is gone, which cut the
space each check-in takes from about 230 to 182 bytes.
